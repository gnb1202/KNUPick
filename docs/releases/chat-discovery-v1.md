## 문제와 변경

“나 컴퓨터공학부 학생인데 어떤 공지 가보는게 좋으려ㅓ나”라는 질문에 주제를 다시 요구하는 동일한 안내가 반복됐다. 기존 계획 호출은 `tool_choice: auto`였고, 도구를 선택하지 않은 모든 응답을 서버가 같은 안내로 바꿨다. 검색 판단 실패와 검색 단서 부족을 구분하지 못한 문제다.

모델은 이제 `search_posts` 또는 `chat_guidance` 중 하나를 명시적으로 선택한다. 전공·관심 주제·활동 목적만 있어도 검색을 시작하도록 프롬프트를 보강했다. 전공으로 캠퍼스·학년·활동유형이나 지원 자격을 추정하지 않는다. 사용자가 직접 말한 전공은 관련 주제 검색의 단서이며 저장 프로필이나 별도 추천 알고리즘과 연결하지 않는다.

`chat_guidance`는 인사·감사·사용법·서비스 밖 질문·검색 단서 부족의 열거형만 받는다. 실제 문장은 서버가 작성한다. 도구 누락·알 수 없는 도구·잘못된 JSON은 `SEARCH_PLAN_FAILED` 오류로 구분하며, 모델의 자유 답변이나 조건을 버린 빈 검색으로 대체하지 않는다. 이전 카드 토큰은 정상 안내에서 유지된다.

일반 검색, 추천, DB·임베딩·검색 정렬, 상세 원문 선택과 UI는 수정하지 않았다. 검색 장애는 이제 정상 0건과 구분한다. 기존 검색 도구의 필터와 의미 검색 결합 한계는 이 수정으로 해결되지 않는다. `required`는 도구 선택을 강제하지만 올바른 의도 판단 자체를 보증하지 않는다. [공식 Function calling 안내](https://developers.openai.com/api/docs/guides/function-calling)를 참고했다.

### 추가한 요청 추적과 장애 구분

- 서버가 만든 UUID를 실행 전부터 사용하며 응답의 `X-Request-Id`, 완료·오류 SSE, 각 단계 로그를 연결한다. 클라이언트가 보낸 요청 ID는 신뢰하지 않는다. 로그 버전은 `legacy-search-trace-v1`이다.
- `chat.request`, `chat.plan`, `chat.search_start`, `chat.search_end`, `chat.response`, `chat.stream_end`에 모드·검색 경로·정규화된 필터·검색어 길이/SHA-256·임베딩 모델/차원·임계값·반환 ID/개수/최고 점수·지연·오류 종류를 필요한 단계마다 기록한다. `chat.response`는 HTTP 응답 준비 시점이고, SSE 종료 결과는 `chat.stream_end`에서 확인한다.
- 새 로그에 대화 원문, 도구 reasoning, 카드 토큰, 벡터, 공지 본문, 상위 API의 오류 객체를 넣지 않는다. 검색어 해시는 원문 복원이 아닌, 사용자가 알려준 검색어와의 비교 용도다. 기존 전역 임베딩/스트림 오류 로그 전체를 개편한 것은 아니다.
- 정상 0건은 `outcome: empty`, 임베딩·벡터 RPC·필터 DB 장애는 `outcome: error`와 서버 오류 코드로 구분한다. 장애 때 답변 생성 호출을 생략하고 `SEARCH_FAILED` SSE를 반환한다. agentic과 vanilla 모두 같은 검색 함수로 이 동작을 적용한다.
- 기존 필터+의미 검색에서 의미 검색어가 무시되는 경우도 `semanticApplied: false`로 드러낸다. 이 결합 검색 한계를 고쳤다는 의미는 아니다. 임계값 아래 점수 관측은 이번 진단에서만 수행했으며, 실제 서비스에 추가 DB 조회나 모델 호출을 넣지 않았다.

최종 무료 검증은 **6파일·67개 테스트**, 타입 검사, 변경 파일 lint, 빌드 통과다. 검색 장애가 정상 0건으로 바뀌지 않는지, 새 로그의 원문 누출 여부, 기존 조건 보존, 동시 요청 ID 분리를 검증했다. 빌드는 가짜 환경 값으로 수행했으며 기존 browser-mapping 안내만 남았다. 운영 검색 결과·전체 답변의 개선은 아직 검증하지 않았다. 다음 수정의 대상은 전공 기반 탐색에 적절한 검색어 구성과 후보 정책이며, 임계값을 일괄 낮추거나 일반 검색·별도 추천 알고리즘을 바꾸지 않는다.
