# ADR-001: 챗봇 검색 — Vanilla RAG → Agentic RAG

- **상태**: 채택
- **작성일**: 2026-05-01
- **컨텍스트**: KNUPick 챗봇(`/api/chat`, `Chatbot.tsx`) retrieval 단계 설계

---

## 1. 배경

KNUPick 우측 하단 챗봇은 사용자가 자연어로 질문하면 학교 공지 중 관련 게시물을 찾아 답변한다. 게시물은 `posts` 테이블에 LLM이 분석한 풍부한 메타데이터(제목·요약·`activity_types[]`·`keywords[]`·`deadline`·`campus`)와 함께 저장돼 있다.

질문 예시:
- "이번달 마감인 공모전 알려줘"
- "근로장학 자리 있어?"
- "통일 관련 공모전"
- "천안 캠퍼스 인턴십"

처음에는 vanilla RAG (임베딩 시맨틱 검색 + LLM 답변 생성) 구조로 시작했다. 그런데 실제 트래픽을 검증해보니 **R(retrieval) 단계가 약해 G(generation)가 일을 못 하는 패턴**이 반복돼, 검색 단을 agentic 구조로 변경하기로 했다.

---

## 2. 시도한 접근과 측정 결과

### 2-1. Vanilla RAG (시맨틱 검색만 사용)

```
사용자 질문 → 임베딩 → pgvector cosine 검색 → 상위 5개 → GPT-4o
```

게시물 임베딩 텍스트는 `제목 + 요약 + 활동유형 + 키워드 + 캠퍼스 + 마감일`(본문 제외).

**임베딩 모델 3가지 비교 (103건 게시물 + 동일 query 4종)**:

| 모델 | 차원 | sim 분포 | 분별력 | "통일 모의 국무회의 경연대회" 매칭 |
|------|-----|---------|-------|--------------------------------|
| OpenAI `text-embedding-3-small` | 1536 | 0.15 ~ 0.22 | 약함 | ❌ (#150 못잡음) |
| OpenAI `text-embedding-3-large` | 1536 | 0.15 ~ 0.22 | 동일 | ❌ |
| 로컬 `bge-m3` (Ollama) | 1024 | 0.30 ~ 0.42 | 약간 나음 | ❌ |

세 모델 모두 다음 패턴이 공통:
- 무관한 게시물이 비슷한 점수로 잡힘 (ex. "통일 공모전" query에 "스마트폰 과의존 특강"이 상위)
- 직접 키워드 포함 query("통일 모의 국무회의")조차 분별력 임계 못 넘김
- threshold를 낮추면 무관 매칭 폭증, 높이면 0건

### 2-2. 진단

문제는 임베딩 모델의 한국어 능력이 아니라 **query ↔ 문서의 비대칭**이었다.

- **사용자 query**: 1~3 단어, 정보량 적음 (`"공모전 알려줘"`)
- **게시물 임베딩 텍스트**: 풍부한 메타데이터, 정보량 많음

이 비대칭이 cosine similarity 절대값을 좁은 구간(0.15~0.42)에 평탄하게 모이게 만든다. 모델을 바꿔도 이 형태의 분포는 안 변한다. 즉 **임베딩 모델은 잘못된 축의 최적화였다.**

추가로, 우리 query 패턴 자체가 시맨틱 검색에 부적합한 종류가 많다:

| Query 종류 | 적합한 검색 방법 |
|-----------|----------------|
| "공모전" (추상 카테고리) | `activity_types`(태그) 매칭 |
| "이번달 마감" (시간 표현) | `deadline` 범위 필터 |
| "천안 캠퍼스" (속성) | `campus` 필터 |
| "통일 모의 국무회의" (고유명사/긴 문장) | 시맨틱 검색이 의미 있음 |

대부분의 사용자 query가 앞 3종에 해당하는데, vanilla RAG는 모든 걸 시맨틱으로 풀려 했다. 구조화된 메타데이터가 이미 있는데 안 쓰는 셈.

## 3. 결정: Agentic RAG (Function Calling 기반 query 이해)

### 3-1. 새 흐름

```
사용자 질문
  ↓
[1] GPT-4o function call: query 의도 분석
    → { activity_types?: [], deadline_range?: {from, to}, campus?, keywords?, semantic_query? }
  ↓
[2] DB 검색: SQL 필터(태그/날짜/캠퍼스) + 보조 임베딩 정렬
  ↓
[3] GPT-4o: 검색 결과를 컨텍스트로 자연어 답변 생성
```

핵심은 **R 단계에 LLM을 한 번 더 두어 query를 구조화 데이터로 번역**한다는 점. 임베딩 검색은 fallback/tie-breaker로 살려두되 주축이 아님.

### 3-2. 왜 오버엔지니어링이 아닌가

거창한 agentic 시스템(multi-agent, ReAct loop, self-RAG, RAG fusion)은 우리에게 불필요. 우리가 도입하는 건 **OpenAI function calling 1회 호출**일 뿐 (코드 50~80줄, 한 라우트 안에 들어감).

이미 다음이 갖춰져 있어 자연스럽게 들어맞는다:
- `activity_types[]`, `keywords[]`, `deadline` 등 구조화 메타데이터가 LLM 분석으로 채워져 있음
- 검색 결과 LLM 답변용 GPT-4o가 이미 사용 중
- 임베딩/pgvector 인프라는 그대로 살려서 보조로 사용

### 3-3. 비용 / 트레이드오프

| 항목 | 변경 |
|-----|------|
| 코드 | `/api/chat` 50~80줄 추가 (function 정의 + 분기 검색) |
| LLM 호출 | 1회 → 2회 |
| 응답 지연 | +0.5~1초 |
| API 비용 | GPT-4o 토큰 ~2배 (요청당 $0.001 미만) |
| 정확도 | 짧은 한국어 query에서 큰 폭 향상 (예상) |

### 3-4. 폐기되지 않는 것

- pgvector + bge-m3 임베딩 인프라는 **유지**. agentic이 추출한 `semantic_query` 필드가 있을 때 fallback으로 쓰임 (예: 고유명사·긴 문장 검색).
- `match_posts` RPC도 유지.
- 게시물 임베딩 백필 파이프라인 그대로.

## 4. 거절한 대안

### 4-1. 임베딩 모델만 더 좋게 (large/bge-m3 등)
→ 측정 결과 본질 해결 안 됨 (위 2-1 표). **거절.**

### 4-2. 임베딩 텍스트 강화 (제목 반복, 키워드 가중치 hack)
→ 단편적 개선만 가능. "이번달", "다음주" 같은 시간 표현·태그 매칭은 임베딩으론 본질적으로 못 풂. **거절.**

### 4-3. 하드코딩 키워드 매핑 ("공모전" → activity_types=1)
→ 자연어 표현(시간/조합/부정어)에 약함. 확장성 없음. **거절.**

### 4-4. Multi-agent / ReAct loop
→ 데이터 규모(현재 ~100건)와 use case 복잡도에 비해 과함. **거절.**

---

## 5. 다음 단계

1. `/api/chat` 라우트에 OpenAI function calling 도입
2. `search_posts` 함수 정의: `{ activity_types?, deadline_from?, deadline_to?, campus?, keywords?, semantic_query? }`
3. function 인자에 따라 SQL 필터 + 임베딩 보조 정렬 분기
4. 시스템 프롬프트 갱신: "추출된 필터로 정확히 검색했음을 사용자에게 자연스럽게 전달"
5. 동일 4개 baseline query로 회귀 테스트 → vanilla RAG 대비 정확도 비교

---

## 6. 회고 메모

- vanilla RAG로 시작한 것 자체는 합리적이었음. 검증 후에 한계가 측정 가능한 수치로 드러나서 다음 결정 근거가 됐다.
- 임베딩 모델 비교(`small` → `large` → `bge-m3`)는 결과적으로 "잘못된 축"이었지만, **"정말 모델 문제인지" 검증한 비용**이라고 보면 의미 있음. 이걸 안 했으면 agentic 도입을 정당화할 근거가 약했을 것.
- 한국어 짧은 query에서 cosine similarity가 평탄하게 분포한다는 점은 우리 도메인 고유의 발견. 비슷한 결정을 마주칠 때 같은 경로를 다시 밟지 않도록 이 문서를 남긴다.
